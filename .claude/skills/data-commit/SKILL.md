# data-commit

변경사항을 **목적 단위로 묶어** 데이터 분석 조직 컨벤션에 맞는 커밋 메시지를 만든다.

분석 저장소는 코드·데이터·노트북·산출물이 한 번에 바뀌는 일이 많아서, 한 덩어리로 커밋하면 나중에 "이 지표는 언제부터 바뀌었지?", "이 데이터는 어떤 코드로 만들었지?"를 추적하기 어렵다. 그래서 커밋을 나누는 기준과 메시지에 남길 정보(데이터 출처·기간·건수·지표 변화)를 컨벤션으로 고정한다. 타입 정의, 스코프 규칙, 본문/푸터 양식, 예시는 [references/convention.md](references/convention.md)에 있다. **메시지를 쓰기 전에 반드시 읽는다.**

## 워크플로

### 1. 변경사항 수집

```bash
git status --short
git diff --stat            # unstaged
git diff --cached --stat   # staged
git log --oneline -15      # 이 저장소의 기존 스타일 확인
```

- 내용 확인은 `git diff <파일>`로 하되, 바이너리(xlsx, parquet, pkl 등)는 diff가 의미 없으므로 파일명·크기·생성한 코드로 판단한다. 가능하면 생성 스크립트나 읽기 코드를 보고 컬럼, 행 수, 기간 같은 내용을 파악한다.
- `.ipynb`는 diff가 JSON이라 노이즈가 크다. 셀의 소스 변경과 출력 변경을 구분해서 본다.
- untracked 파일도 반드시 포함해서 분류한다. 단, `.claude/`처럼 도구 설정 디렉터리는 사용자에게 포함 여부를 확인한다.
- 이미 staged된 항목이 있으면 사용자가 의도한 묶음일 수 있으니 존중하고, 나누고 싶은 경우에만 제안한다.

### 2. 커밋 전 점검 (먼저 사용자에게 알린다)

되돌리기 어려운 것부터 걸러낸다. 커밋 히스토리에 한번 들어간 민감정보는 지우기 매우 어렵기 때문이다.

- 개인정보(이름, 전화번호, 주민번호, 이메일, 정확한 위치) 의심 컬럼이 있는 원천 데이터
- `.env`, 키·토큰·접속정보가 든 파일, SQL/노트북 안의 하드코딩된 비밀번호·DB 주소
- 대용량 파일(대략 5MB 이상)이나 모델 바이너리 → `.gitignore`, Git LFS, DVC 등을 권고
- 출력이 그대로 남은 노트북(수치·개인정보가 셀 출력에 노출될 수 있음)

문제가 있으면 해당 파일은 커밋 계획에서 빼고 이유를 설명한다.

### 3. 논리적 단위로 그룹핑

기준은 디렉터리가 아니라 **변경의 목적**이다. 자세한 판단 규칙은 convention.md의 "그룹핑 규칙"을 따른다. 핵심만 요약하면:

- 데이터(`data`)와 그것을 다루는 코드(`feat`, `pipeline` 등)는 기본적으로 분리한다. 데이터는 재생성/교체가 잦고 코드와 리뷰 관점이 다르기 때문이다. 다만 코드가 만든 작은 더미/샘플 데이터는 코드와 함께 묶어도 된다.
- 리팩터링과 기능 추가, 버그 수정은 섞지 않는다.
- 노트북과 그 노트북이 의존하는 모듈 변경은 목적이 같으면 한 커밋으로 묶는다.
- 포맷팅·오타·설정 같은 잡일(`style`, `chore`)은 별도 커밋으로 뺀다.
- 한 파일 안에 서로 다른 목적의 변경이 섞여 있으면 `git add -p`로 나눌 수 있는지 검토하고, 어려우면 사용자에게 알린다.

### 4. 메시지 작성

convention.md의 형식을 따른다: `타입(스코프): 제목` + (필요하면) 본문 + (필요하면) 푸터. 기존 커밋이 한글이므로 한글로 쓴다. 제목은 "무엇을 했는지"를 명사형/동사 원형으로 간결하게 쓰고, 본문에는 "왜", 그리고 분석 저장소에서 특히 중요한 **재현·검증 정보**(데이터 출처, 기간, 건수, 파라미터, 지표 변화)를 남긴다. 확인하지 못한 수치는 지어내지 않고 비워두거나 사용자에게 묻는다.

### 5. 계획 제시 → 확인 → 커밋

커밋을 실행하기 전에 아래 형태로 계획을 보여주고 사용자 확인을 받는다. 커밋은 히스토리를 만드는 행동이므로, 사용자가 "바로 커밋해줘"라고 분명히 말한 경우가 아니면 확인을 먼저 받는다.

```
커밋 계획 (총 N개)

[1] data(bus): 노선/하차 더미 데이터 추가
    - data/bus_routes.xlsx
    - data/bus_alighting.xlsx
    (메시지 전문)

[2] feat(bus): ...
    - make_dummy_data.py
    - read_data.py

제외/주의: .claude/ (도구 설정, 포함 여부 확인 필요)
```

승인되면 커밋별로 **파일을 명시해서** `git add <경로...>` 후 `git commit`을 실행한다. `git add -A` / `git add .`은 점검에서 걸러낸 파일까지 딸려 들어가므로 쓰지 않는다. 여러 줄 메시지는 `-m`을 여러 번 쓰거나 파일/here-string으로 전달한다. 훅이 실패하면 `--no-verify`로 우회하지 말고 원인을 고친다.

커밋 후 `git log --oneline -N`으로 결과를 보여준다. push는 요청이 없으면 하지 않는다.

## 참고

- 시스템/사용자 지침에 커밋 메시지 끝에 붙일 공동 작성자(Co-Authored-By) 줄이 지정되어 있으면 푸터 맨 끝에 그대로 붙인다.
- 변경이 한 가지 목적뿐이면 억지로 나누지 않는다. 커밋 1개가 맞는 경우도 많다.
- 사용자가 타입이나 스코프를 직접 지정하면 그 선택을 따른다.
