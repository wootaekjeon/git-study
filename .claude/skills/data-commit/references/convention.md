# 데이터 분석 조직 커밋 컨벤션

[Conventional Commits 1.0](https://www.conventionalcommits.org/ko/v1.0.0/)(Angular 컨벤션 계열)을 뼈대로 하고, 데이터 분석 업무에 맞게 타입·본문·푸터를 확장했다. 목표는 두 가지다.

1. `git log`만 봐도 **어떤 데이터/지표/모델이 언제 왜 바뀌었는지** 추적된다.
2. 분석 결과를 **다시 재현**할 수 있는 단서(출처, 기간, 파라미터, 시드)가 남는다.

## 목차
1. 형식
2. 타입
3. 스코프
4. 제목 규칙
5. 본문 규칙
6. 푸터 규칙
7. 그룹핑 규칙

---

## 1. 형식

```
<타입>(<스코프>): <제목>

<본문>

<푸터>
```

- 스코프, 본문, 푸터는 선택. 제목만으로 충분하면 생략한다.
- 제목·본문·푸터 사이는 빈 줄 한 줄.

## 2. 타입

### 일반 개발 타입

| 타입 | 사용 시점 |
|---|---|
| `feat` | 새 분석 로직, 지표, 함수, 기능 추가 |
| `fix` | 버그·계산 오류·잘못된 집계 조건 수정 |
| `refactor` | 결과가 달라지지 않는 구조 개선 |
| `perf` | 쿼리/연산 속도·메모리 개선 |
| `test` | 테스트, 데이터 검증(validation) 코드 |
| `docs` | README, 데이터 사전, 분석 가이드 등 문서 |
| `style` | 포맷, 공백, import 정렬 등 동작 무관한 변경 |
| `chore` | 설정, 의존성, .gitignore 등 잡무 |
| `build` | 패키징, 환경(requirements, conda env, Dockerfile) |
| `ci` | CI/CD, 스케줄러(Airflow 등) 설정 |
| `revert` | 이전 커밋 되돌리기 |

### 데이터 분석 특화 타입

| 타입 | 사용 시점 | 예 |
|---|---|---|
| `data` | 데이터 파일 추가·갱신·삭제, 스키마/컬럼 변경, 더미·샘플 데이터 | `data(bus): 2026-09 하차 데이터 추가` |
| `eda` | 탐색적 분석 노트북/스크립트 (결론 전 단계) | `eda(bus): 노선별 하차 분포 탐색` |
| `query` | SQL/쿼리 추가·수정 | `query(bus): 일별 하차 집계 쿼리 추가` |
| `pipeline` | ETL, 전처리, 집계 배치 등 데이터 흐름 코드 | `pipeline(bus): 하차 데이터 정제 단계 추가` |
| `model` | 피처, 모델 학습/평가 코드, 하이퍼파라미터 | `model(churn): LightGBM 피처 12개 추가` |
| `exp` | 실험 설정과 결과 기록 (A/B 테스트, 모델 비교 등) | `exp(churn): 학습 윈도우 30일 vs 60일 비교` |
| `viz` | 차트, 대시보드, 시각화 코드 | `viz(bus): 시간대별 하차 히트맵 추가` |
| `report` | 리포트, 인사이트 문서, 발표 산출물 | `report(bus): 9월 노선 분석 리포트 초안` |

> 분석 결과 해석이나 결론을 담은 문서는 `report`, 사용법/설명 문서는 `docs`다.

## 3. 스코프

스코프는 **변경이 속한 분석 도메인·데이터셋·지표**를 쓴다. 파일 경로가 아니다.

- 소문자 영문(kebab-case) 권장: `bus`, `churn`, `ad-roas`, `user-segment`
- 한 커밋이 여러 도메인에 걸치면 스코프를 생략하거나 가장 핵심인 것 하나만 쓴다 (쉼표로 나열하지 않는다).
- 저장소 안에서 스코프를 새로 만들기 전에 `git log`에서 이미 쓰는 스코프가 있는지 확인하고 재사용한다.
- 저장소 전반의 설정·문서는 스코프를 생략한다.

## 4. 제목 규칙

- 한글로 작성하고, 영문 약어·고유명사는 그대로 쓴다 (SQL, ETL, LightGBM).
- "무엇을 했는지"를 간결하게. `추가`, `수정`, `제거`, `개선`, `분리`처럼 동작이 드러나게 끝낸다.
- 50자 안팎, 마침표 없음.
- "수정", "업데이트", "작업"처럼 내용 없는 제목은 쓰지 않는다.

## 5. 본문 규칙

제목으로 설명이 안 되는 경우에만 쓴다. 불릿(`-`)으로 간결하게, **왜**를 중심으로 쓴다. 데이터 분석 변경에서는 아래 항목 중 해당되는 것을 남긴다.

- **데이터**: 출처(시스템/테이블/수집 방식), 기간, 행·컬럼 수, 주요 컬럼, 더미 여부
- **로직 변경**: 집계 기준/필터/정의가 어떻게 바뀌었고 왜 바뀌었는지
- **영향**: 지표 값의 전후 비교 (예: 평균 하차 인원 120 → 98), 기존 결과와 달라지는 부분
- **재현**: 랜덤 시드, 주요 파라미터, 사용한 환경/버전
- **검증**: 어떤 방법으로 확인했는지 (건수 대조, 샘플 확인 등)

확인하지 않은 수치는 쓰지 않는다. 틀린 수치가 히스토리에 남는 것이 빈 칸보다 나쁘다.

## 6. 푸터 규칙

- `Refs: #123` / `Closes: #123` — 이슈·티켓 연결
- `BREAKING CHANGE: 설명` — 스키마(컬럼 삭제·이름 변경·타입 변경), 지표 정의 변경처럼 **하위 소비자(대시보드, 다운스트림 노트북)가 깨질 수 있는 변경**
- `Data-Source: 출처` — 원천 데이터 출처를 본문에 쓰기 길 때
- `Co-Authored-By: ...` — 지침에 지정된 경우 맨 마지막 줄

## 7. 그룹핑 규칙

변경 파일을 아래 순서로 판단해 커밋 단위를 만든다.

1. **목적이 같은가?** 같은 문제를 해결하려고 바뀐 파일끼리 묶는다. (예: 지표 정의 수정 → 쿼리 + 그 쿼리를 쓰는 노트북 셀)
2. **데이터 vs 코드 분리.** `data/` 아래 파일과 코드는 기본 분리한다. 예외: 코드가 생성한 작은 더미/샘플 데이터를 생성 코드와 함께 추가할 때는 한 커밋도 허용.
3. **타입 혼합 금지.** 한 커밋에 `refactor`와 `feat`/`fix`가 섞이면 나눈다. 리뷰와 revert가 쉬워진다.
4. **산출물은 원인과 함께.** 코드 변경으로 인해 재생성된 리포트·차트 이미지는 해당 코드와 같은 커밋, 단 재생성이 대량이면 별도 커밋 허용.
5. **잡일 분리.** 포맷팅, 설정, `.gitignore`, 의존성은 `style`/`chore`/`build`로 따로.
6. **생성물·캐시는 제외.** `__pycache__`, `.ipynb_checkpoints`, 임시 파일 등은 커밋하지 않고 `.gitignore` 추가를 제안한다.
7. 커밋 순서는 **의존 순서**로. 데이터/스키마 → 파이프라인/쿼리 → 분석/모델 → 시각화/리포트 → 문서.

## 8. 예시

**데이터 추가 (이 저장소의 `5f1c489`를 컨벤션대로 나누면)**

```
data(bus): 버스 노선/하차 더미 데이터 추가

- bus_routes.xlsx: 노선 마스터 (더미)
- bus_alighting.xlsx: 노선별 하차 기록 (더미)
```

```
feat(bus): 더미 데이터 생성 및 xlsx 읽기 코드 추가

- make_dummy_data.py: 더미 데이터 생성 (랜덤 시드 고정 여부 확인 필요)
- read_data.py: xlsx 로드 후 확인용 출력
```

**지표 정의 수정 (BREAKING)**

```
fix(retention): D7 리텐션 분모를 가입자 전체에서 활성 가입자로 변경

- 휴면 전환 계정이 분모에 포함되어 리텐션이 과소 집계되던 문제 수정
- 기존 대비 D7 리텐션 31.2% → 38.5% (2026-09 코호트 기준)

BREAKING CHANGE: D7 리텐션 값이 변경되어 기존 대시보드 수치와 직접 비교 불가
```

**모델 / 실험**

```
model(churn): 최근 7일 접속 빈도 피처 추가

- 접속 횟수, 평균 세션 길이, 마지막 접속 후 경과일
- 검증 AUC 0.812 → 0.826 (seed=42, 5-fold)
```

```
exp(churn): 학습 윈도우 30일 vs 60일 성능 비교

- 60일 윈도우가 AUC +0.004, 학습 시간 1.8배
- 결과표는 experiments/churn_window.md 참고
```

**노트북 / 시각화 / 쿼리**

```
eda(ad-roas): 매체별 ROAS 분포 및 이상치 탐색
viz(bus): 시간대별 하차 인원 히트맵 추가
query(sales): 주간 매출 집계 쿼리에서 환불 건 제외
```

**잡일**

```
chore: 노트북 체크포인트와 data 임시 파일 .gitignore 추가
build: requirements에 openpyxl 추가
docs(bus): 데이터 사전에 컬럼 설명 추가
```

## 9. 타입 선택이 애매할 때

| 상황 | 선택 |
|---|---|
| 노트북에서 탐색하다가 쿼리도 같이 수정 | 목적이 탐색이면 `eda`, 쿼리 로직 수정이 핵심이면 분리 |
| 결과가 달라지는 코드 정리 | `refactor`가 아니라 `fix`/`feat` |
| 더미 데이터 생성 코드 | 처음 만들면 `feat`, 데이터 재생성만이면 `data` |
| 실험 코드 + 결과 기록 | 코드는 `model`, 결과 기록은 `exp` (한 커밋이면 `exp`) |
| 대시보드 쿼리 수정 | 화면 변경이면 `viz`, 데이터 로직이면 `query` |
